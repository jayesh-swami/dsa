**1.** A variable-size window has a `while` that moves `l` forward inside a `for` that moves `r`. Why is the whole scan O(n) and not O(n²)?

**Answer:** Assuming the while condition stops until `l` reaches `r`, each element will only be visited twice, once by `r` in `for` and once by `l` so O(n);

> ✅ Correct. The key fact is that **`l` never moves back**, so across the whole scan it moves at most `n` times in total. The stopping condition matters less. Each element enters the window once and leaves at most once.

**2.** Contains Duplicate II, at index `i` with distance `k`: (a) which **indices** should the set hold just before you check `nums[i]`? (b) Which element do you erase at step `i`?

**Answer:** If `i <= k` then all indices upto `i` (i not included) and for `i > k`, indices from `i-k` to `i-1`

> 🟡 (a) is right: `[max(0, i - k), i - 1]`. (b) wasn't answered. When `i > k`, erase `nums[i - k - 1]`, the index that just dropped out of `[i - k, i - 1]`.

**3.** What is the space complexity of the set version, and why is it written with a `min`?

**Answer:** The space complexity is O(min(n,k)). It is minimum because if `n < k` at most we put the whole array in set and if `k <= n` we only put at most k distinct elements within the window.

> ✅ Correct.

**4.** The map version stores value → index, and keeps only the **latest** index for each value. Why is the latest index enough?

**Answer:** Because if an older index is within the window and satisfies, the latest one will surely satisfy the condition since it will be within the window as well.

> ✅ Correct. In one line: the latest earlier copy is the **closest** one to `i`, so if any copy is within `k`, that one is.

**Coding question (Maximum Average Subarray I, LC 643).** Given `nums` and `k`, return the largest average of a contiguous subarray of length exactly `k`. `1 ≤ k ≤ n ≤ 10⁵`, `|nums[i]| ≤ 10⁴`. Write it as you would in an interview, without compiling. Then answer:
- (a) Time and space complexity.
- (b) What type do you use for the running sum, and why is it safe for these constraints?
- (c) One line on how you turn the sum into the average.

```cpp
double findMaxAverage(const vector<int>& nums, int k) {
    long long runningSum = 0;
    long long maxSum = INT_MIN;

    for(int i = 0; i < (int) nums.size(); i++) {
        if(i < k) runningSum += nums[i];
        else {
            maxSum = max(maxSum, runningSum);
            runningSum += nums[i] - nums[i-k];
        }
    }

    maxSum = max(maxSum, runningSum);

    return (double) maxSum / (double) k;
}
```

**Answer (a)–(c):** a) Time -> O(n) Space -> O(1) 
b. I use `long long` since the sum can go upto `10^9` and `long long` can easily accomodate it
c. Cast to `double` then divide by window size.

> ✅ Correct, including `k == n` (the `else` never runs, and the `max` after the loop picks up the only window). (a), (b) and (c) are all right, and casting before dividing avoids integer division.
> - (b) For the record, `int` would also work: `10⁵ · 10⁴ = 10⁹ < 2.147·10⁹`. `long long` is still the right habit, and you checked the bound.
> - `INT_MIN` as a starting value works here because no window sum can go below `-10⁹`. Starting from a real value is safer (the Kadane lesson from Q1): sum the first `k`, set `best = sum`, then loop from `i = k`. That also removes the `if`/`else` and the extra `max` after the loop:
>   ```cpp
>   long long sum = 0;
>   for (int i = 0; i < k; i++) sum += nums[i];
>   long long best = sum;
>   for (int i = k; i < (int) nums.size(); i++) {
>       sum += nums[i] - nums[i - k];
>       best = max(best, sum);
>   }
>   return (double) best / k;
>   ```

**6.** "Grow `r`, shrink `l` while the window sum is `> k`" finds subarrays with sum `k` when every value is positive. Why does it break when values can be negative, and what do you use instead?

**Answer:** When every value is positive the sum can only increase by adding more elements, so incrementing `l` makes sense. But when there are negative values, we cannot say for certain that the sum by adding another element is going to grow and there might be a subarray that we might miss that starts at `l` and the current sum is `> k` because there are negative elements past our `r` pointer.

> 🟡 The "why" is right: with negatives the window sum isn't monotonic, so shrinking when it's `> k` can discard a start whose sum would come back down to `k` later. The second part wasn't answered: use **prefix sum + a hash map of prefix counts**, seeded with `{0: 1}`, which is O(n).

**7.** `s` is an `unordered_set<int>`. What does `s.insert(x).second == false` tell you, and why use it instead of `contains` followed by `insert`?

**Answer:** This statement does an insert and check in one go. `s.insert()` returns a pair whose `second` property tell us if the element was actually inserted. We should use it instead because this is one operation instead of two.

> ✅ Correct. `false` means `x` was already in the set.

**8.** `if (mp.contains(n) && i - mp[n] <= k) return true;` How many hash lookups does this do when `n` is present? Rewrite it with a single lookup.

**Answer:** This does 2 hash lookups when n is present. single lookup using `mp.find()` and then checking if it is `mp.end()`. If it is not then checking the value from the returned result of `mp.find()` (I dont know how to exactly do this tho)

> 🟡 The count (2) and the idea are right; the code was missing. `find` returns an iterator to a `pair<const Key, Value>`, so the value is `it->second`:
> ```cpp
> auto it = mp.find(n);
> if (it != mp.end() && i - it->second <= k) return true;
> ```
> The `mp[n] = i;` that follows is a third lookup. To do the whole step in one, use `try_emplace`, which inserts only if the key is missing and returns the same `(iterator, inserted)` pair as `insert`:
> ```cpp
> auto [it, inserted] = mp.try_emplace(n, i);
> if (!inserted) {
>     if (i - it->second <= k) return true;
>     it->second = i;
> }
> ```

**9.** What goes wrong in `for (int i = 0; i < nums.size() - k; i++)` when `nums.size() < k`?

**Answer:** `nums.size()` returns an unsigned int and then `- k` on that would lead to `undefined` loop behaviour.

> 🟡 You spotted the unsigned `size()`, which was blank in Q1, so that's progress. Two corrections:
> - The wrap itself is **not** UB. Unsigned arithmetic is defined modulo 2⁶⁴, so `nums.size() - k` becomes about 1.8·10¹⁹.
> - What goes wrong: `i < 1.8·10¹⁹` stays true, so the loop runs past the end, and `nums[i]` out of bounds is the UB (usually a crash).
> - Fix: `int n = nums.size();` first, then `i < n - k` (or `i + k < n`).

**10.** ★ For "longest window that satisfies a rule" (e.g. no repeated characters), do you update the answer after **growing** `r` or after **shrinking** `l`? Why?

**Answer:** After growing `r` since we grow `r` when the window can still be expanded and the rule is not violated. We shring `l` when the rule is not being satisfied.

> 🟡 Correct for the template you described, where you only grow when the window stays valid. The rule underneath is: **record the answer only when the window is valid.**
> - The standard template always grows `r` in a `for` loop, and the new element can break the rule. So the order is: add `s[r]`, shrink `l` **while** invalid, **then** record `r - l + 1`. Recording right after growing would count an invalid window.
> - For the **shortest** valid window (Minimum Window Substring) it flips: record **inside** the shrink loop, before each shrink, while the window is still valid.
