**1.** Longest Substring Without Repeating Characters, with `last[x]` = the latest index of `x`. (a) Why `l = max(l, last[x] + 1)` and not just `l = last[x] + 1`? (b) Give a short string where the version without `max` returns the wrong length, and say what it returns.

**Answer:**
a. max because `l` might move backwards to the point where we have duplicates when there are multiple duplicates.
b. abcdbazrt -> Here when we get to the last `a` the l would move to index `1` and the subsequent `r-l+1` window would ignore the duplicate `b`. It would return `8`.

> ✅ Both parts right. `last[a] = 0` is stale, because it's already left of `l = 2`, so without the `max` the window grows back over the second `b`. It returns 8; the correct answer is 7 (`cdbazrt`). The shortest example is `abba`, which returns 3 instead of 2.

**2.** Longest Repeating Character Replacement (at most `k` changes). (a) The window `[l, r]` is valid exactly when ___ (one inequality). (b) Why is it fine that `maxf` never decreases when `l` moves?

**Answer:** 
a. `r - l + 1 - maxf <= k`
b. Because we have already accounted for the maximum possible window until now. Any decrease in `maxf` would be a suboptimal window than the current one.

> ✅ Both right. A more precise way to say (b): the answer is `maxf + k`, so it can only grow when `maxf` grows. While `maxf` is stale, the window slides at its current size and never records anything larger than the best already seen.

**4.** Value Counters: `b_x = L - R`, where `L` = smaller values to the left of `x` and `R` = larger values to the right. Write `pos_x` (0-indexed) as a sum of two counts, then replace one of them using a total, to get `pos_x = b_x + n - x`.

**Answer:**
`pos_x = L + n - R - x`
Since `b_x = L - R`
`pos_x = b_x + n - x`

> 🟡 The result is right, but the two steps the card asked for are missing, and those steps are the actual argument:
> 1. `pos_x` = the number of values to the left of `x` = `L + G`, where `G` = larger values to the left.

**Answer:**

**9.** `ios::sync_with_stdio(false); cin.tie(nullptr);` (a) What does each of the two lines change? (b) What must you then avoid, and when does the second line need extra care?

**Answer:**

a. The first stops the sync with standard io buffer. The second stop the flush to after every cin (a bit weak on this one, lets count this one as I dont know)
b. No clue

> ❌ As you asked, this one is counted as not known. The answer:
> - `sync_with_stdio(false)`: `cin`/`cout` stop going through C's `stdio` buffers and use their own, which is much faster.
>   - **Avoid:** mixing `printf`/`scanf` with `cout`/`cin`. The two sets of buffers flush separately, so output can come out in the wrong order.
> - `cin.tie(nullptr)`: by default `cin` flushes `cout` before every read. Untying stops that.
>   - Fine for normal problems, where all input comes before the output matters.
>   - **Care:** in **interactive** problems you must flush yourself after each query (`cout << ... << endl` or `cout.flush()`). Otherwise the judge never sees the query and you get *Idleness limit exceeded*.
> - Related: use `'\n'` rather than `endl` in normal problems, because `endl` flushes on every line.
